# Process Identity and Claude Channel Recovery

Date: 2026-09-01

Status: Approved design

## Problem

Antiphon uses a process id plus `ps lstart` to distinguish a live process from
a recycled pid and to join the two writers of a Codex peer. The current reader
inherits its caller's locale and timezone, then slices the rendered line at 24
characters. The same live process can therefore acquire different fingerprints
when the registry writer and reader have different `TZ` or `LC_TIME` values.

This causes two independent failures:

1. `_record_alive` can prune a live endpoint as if its pid had been recycled.
2. `owner_key` can stop joining a Codex endpoint with its session record, leaving
   the peer live but permanently unroutable.

There is a durable follow-on failure on the Claude side. The Node channel
process continues serving its deterministic named socket after a false registry
prune. A later channel process claims the alias, observes the already-live
socket, releases its own claim, and leaves the original listener unregistered.
Every later restart repeats that state. The existing identity fix correctly
signs the new session's messages but cannot make the original listener
addressable again.

## Goals

- Make process fingerprints stable across timezone and locale differences.
- Preserve pid-reuse protection for newly written records.
- Upgrade existing records without pruning a live process because an old
  rendered fingerprint cannot be reproduced.
- Keep the Codex endpoint/session join stable under the same process identity
  rules.
- Let a current Antiphon Claude listener re-advertise itself when its registry
  record is missing.
- Never let a new process register another process's endpoint on its behalf.
- Never adopt or unlink an arbitrary process merely because it holds the
  deterministic socket path.
- Keep `doctor` read-only.

## Non-goals

- Killing an orphaned process automatically.
- Repairing an old listener that does not implement the recovery control
  protocol. It remains fail-closed and requires a restart.
- Adding pending delivery, acknowledgement, retry, or reply correlation.
- Sending message content in a recovery probe or a refused-send diagnostic.
- Treating every BACKLOG item as part of this P0.

## Design

### 1. Canonical, versioned process fingerprints

Every new process observation runs `ps` with both `LC_ALL=C` and `TZ=UTC` in
the child environment. Parsing uses the full canonical `lstart` fields rather
than assuming that the start time occupies 24 characters in an inherited
locale.

The stored fingerprint is explicitly versioned. New endpoint records carry a
version marker beside `birth`, and new owner keys carry a versioned form. The
version distinguishes canonical values from the unmarked strings written by
0.3.3 and earlier; a reader must not guess which environment produced an
unmarked value.

The process-info helper is the single source used by both endpoint birth and
`owner_key`. `doctor` must use that helper or the same canonical environment so
it cannot disagree with the registry about one process.

### 2. Legacy migration and liveness

New records use strict comparison:

- pid absent or not alive: dead;
- canonical fingerprint unavailable now: unknown, therefore not prunable;
- canonical fingerprint equal: live;
- canonical fingerprint different: pid was recycled, therefore dead.

An existing record without the new version marker is legacy. Its rendered
fingerprint cannot safely be compared with the new UTC/C value. While its pid
is alive it is treated as unverifiable and not pruned. The next successful
registration by its owner rewrites it in the canonical format.

This deliberately gives a legacy record the pre-fingerprint PID-only behavior
during rolling upgrade. It avoids deleting every live peer once, at the cost of
temporarily losing pid-reuse protection for records whose rendering provenance
is unknown. New records regain the protection immediately.

### 3. Owner-key joins

New endpoint and session records use the same versioned owner key generated by
the canonical process helper. Two new records therefore join identically across
host environments.

Legacy keys continue to join each other by exact equality. A legacy key and a
new key do not join by pid alone: doing so could attach a stale session record
to an unrelated process after pid reuse. Mixed-format records stay visible but
unroutable, and diagnostics tell the operator to restart the older writer so it
can refresh its record.

Validation accepts the legacy form for reading and rolling compatibility and
the new form for writes. It does not accept arbitrary environment-provided
identity.

### 4. Listener-owned registry recovery

The deterministic named socket remains the only recovery address, but a bare
successful connect is not proof that Antiphon owns it.

Current Node listeners recognize a versioned, content-free control request. A
reassert request contains only:

- a protocol marker and version;
- the requested alias;
- a random nonce used to bind the response to the request.

It contains no user message or transcript content. The listener validates that
the alias is its own, invokes the existing `register_peer` path with its own
`process.pid`, alias, and socket address, and returns a control response naming
the protocol version, nonce, and whether registration succeeded. The caller
then re-reads the registry. Only the listener can publish its endpoint.

An arbitrary socket binder cannot be adopted merely by returning generic JSON.
Recovery requires the versioned response and a fresh registry record written by
the listener. An old Antiphon listener may answer an unsupported payload with a
normal error, but it cannot produce the control response and registry record;
the caller therefore remains fail-closed.

### 5. Startup sequence

For a usable name, startup proceeds as follows:

1. Resolve identity independently so replies are signed with the configured
   alias on every route.
2. If the deterministic socket answers, check whether a live registry endpoint
   already describes it.
3. If the record is missing, ask the listener to reassert itself and verify the
   resulting registry record.
4. If a live registered listener now owns the socket, do not claim, unlink, or
   bind it. This process remains reply-capable but unreachable and reports the
   actual owner conflict.
5. If no listener answers, claim the registry alias atomically and bind the
   socket as today.
6. If a bind race reveals a listener after the claim, release only this
   process's claim, request listener-owned reassertion, and report the verified
   result.

The sequence preserves the registry lock as the winner for new servers while
giving an existing Antiphon listener a safe way to restore its own missing
record.

### 6. Named send recovery

An explicit named send still resolves through the registry first. If no live
endpoint holds the requested alias, the sender may make one bounded recovery
attempt against `sha256(projectDir + "\0" + alias)`:

1. send the content-free reassert control request;
2. re-resolve the named target from the registry;
3. if it is now live, deliver the original message exactly once;
4. otherwise preserve the existing `no-peer` refusal and passive-page fallback.

The control request never travels to the Claude host as a channel notification.
The existing content-free refused-attempt notification remains available when
the socket is live but recovery does not establish a routable peer. No pending
delivery state is created.

### 7. Doctor and diagnostics

`doctor` continues to probe and report but never sends a reassert request,
writes a registry record, unlinks a socket, or kills a process.

Its states distinguish:

- live and registered;
- live Antiphon listener with no endpoint record;
- socket occupied by an unverified listener;
- registry endpoint whose process is dead;
- mixed legacy/new owner records that cannot be joined safely.

The repair text tells a user to restart an old listener when automatic recovery
is unavailable. It does not expose another installation's paths or processes.

## Error handling and safety invariants

- Every startup route settles `identitySettled`; reply tools never wait forever.
- Registration failure never changes the configured sender identity.
- Only the process serving a socket registers that socket's endpoint.
- A recovery request is bounded by the existing channel byte and timeout limits.
- A malformed, mismatched, or unsupported control response is a failed recovery.
- Failed recovery does not consume or queue the user's message.
- Recovery is attempted at most once per resolution/send operation.
- Shutdown removes only the socket and registry claim owned by that process.
- Tests use throwaway projects and socket directories; live cursors and peer
  registries are never modified.

## Test strategy

Tests are written and observed failing before production changes.

Python unit and integration cases:

- one live pid observed under two timezones produces one canonical fingerprint;
- locale variation does not change the fingerprint or parsing;
- a legacy birth mismatch does not prune a live endpoint;
- a canonical birth mismatch does prune a recycled pid;
- new owner keys match across environments;
- mixed-format owner records fail closed instead of joining by pid;
- `doctor` reports recovery states without changing any file.

Node and cross-process cases:

- a listener with a missing endpoint reasserts its own pid and becomes routable;
- a second named channel does not overwrite or unlink that listener;
- an arbitrary socket binder is not adopted;
- an old/unsupported listener remains fail-closed with actionable output;
- an explicit named send recovers, re-resolves, and delivers content once;
- failed recovery carries no content in its diagnostic request;
- every startup route settles reply-tool identity.

Release verification:

1. focused Python and Node tests;
2. complete `npm test`;
3. clean-tree `test/e2e/fresh-user.sh` on the exact candidate commit;
4. independent read-only review by a separate agent on that SHA;
5. no push, version bump, or publish until the verified local result is shown to
   the user.
